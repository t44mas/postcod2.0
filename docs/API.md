# B2B API · Почта Премиум

API: `http://127.0.0.1:8000/api/v1`. Интерактивный контракт: [Swagger UI](http://127.0.0.1:8000/docs), [OpenAPI JSON](http://127.0.0.1:8000/openapi.json).

Это локальный демонстрационный модуль участника №4. B2C и операционные модули команды не включены. Названия, цены и преимущества — гипотезы проекта; оплата имитируется.

## Запуск

Из корня проекта при запущенном Docker Desktop:

```powershell
python scripts/start.py
```

Команда сохраняет существующий `.env` или генерирует случайный локальный пароль, затем собирает и запускает PostgreSQL, API и сайт. API применяет Alembic-миграции и идемпотентно создаёт справочники и демо-пользователей. БД хранится в именованном Docker-томе. Контейнерные порты опубликованы только на `127.0.0.1`.

## Демо-сессии и серверные права

`POST /auth/demo/login`, тело `{"persona":"demo_admin"}`, возвращает `accessToken`, `tokenType`, `expiresAt`. Токен передаётся как `Authorization: Bearer <accessToken>`. Он живёт 12 часов; в БД хранится SHA-256-хеш. `demo_other_admin` — независимая тестовая персона для изоляционных проверок.

Демо-вход намеренно доступен без настоящего пароля. Он нужен для локального показа синтетических данных и не является регистрацией/входом для промышленного продукта. `DEMO_AUTH_ENABLED=false` отключает выдачу демо-сессий, переключение и сброс. Перед публичным развёртыванием нужна отдельная настоящая аутентификация. Серверные проверки роли и принадлежности компании при этом уже действуют для каждого выданного токена.

`POST /auth/demo/employees/{membershipId}` доступен только администратору своей компании: выдаёт ограниченную сессию выбранной демо-персоны. Даже если участнику назначена роль администратора, эта специальная сессия имитирует именно сотрудника. Она не открывает корпоративные отчёты, сотрудников, счета и полный снимок компании. Отключённый сотрудник получает отказ также по ранее выданному токену.

Компания определяется по сессии и активному членству, а не из тела запроса. Pydantic запрещает лишние поля. Передать `companyId`/`employeeId` в активацию, чтобы списать бонус за чужого пользователя, нельзя.

## Тела запросов

Атомарное подключение:

```json
{"name":"ООО Демо Маркет","tariffId":"plus"}
```

Добавление сотрудника:

```json
{"name":"Анна Демо","role":"company_employee"}
```

Роли: `company_admin`, `company_employee`; статусы: `active`, `disabled`. Владелец компании не входит в список добавляемых сотрудников и не занимает активное место тарифа. Отключённая запись сохраняет историю. Превышение 10 мест Start / 30 мест Plus проверяется также при повторном включении.

Назначение:

```json
{"employeeId":"membership-id","code":"shipping","enabled":true,"limitKopecks":10000}
```

Личный лимит не резервирует общий остаток. Его нельзя уменьшить ниже использованного. `shipping` есть в обоих тарифах; `packaging` — в Plus.

Активация с токеном сотрудника:

```json
{"code":"shipping","originalKopecks":35025,"requestKey":"unique-request-id"}
```

Одна операция — одна услуга. Положительная исходная цена — до 1 000 000 ₽. Фактическая скидка равна меньшему из тарифной скидки и исходной цены. Финансовые значения счетов, операций и счётчиков БД — целые копейки. В `/economics/scenarios` входные гипотезы имеют отдельные единицы: исходные расходы в рублях, churn в базисных пунктах; расчётные денежные результаты в копейках. Единицы явно указаны в метаданных ответа.

## Транзакции и повторные запросы

Операции используют SQLAlchemy 2 и PostgreSQL. Изменения компании сериализуются блокировкой её строки; общая и персональная строки лимита дополнительно блокируются `SELECT ... FOR UPDATE`. В одной транзакции проверяются подписка, срок, права, оба остатка, записывается использование и обновляются счётчики. Ошибка откатывает транзакцию.

Уникальность `(subscription_id, request_key)` закреплена в БД. Повтор своего запроса с теми же данными возвращает ту же операцию без второго списания. Тот же ключ с другими данными даёт `409 idempotency_conflict`. Повтор оплаты не изменяет даты оплаченной подписки. Создание компании сериализуется по владельцу до появления самой компании.

Сводки читаются под той же блокировкой компании, чтобы журнал и счётчики не смешивали разные моменты конкурентных изменений. Суммы дополнительно защищены SQL CHECK-ограничениями; принадлежность сотрудников проверяется сервером.

## Даты, ответы и ошибки

Даты API — ISO 8601 UTC, UI отображает Москву. Период оплаты — календарный месяц с ограничением последним днём следующего месяца. Фильтры `employeeId`, `from=YYYY-MM-DD`, `to=YYYY-MM-DD` у журнала/отчёта используют московские календарные сутки; `to` включительно. Фильтр сотрудника не расширяет доступ сотруднического токена.

Ответ `/companies/me/state` совместим с `DemoConnection`: `company`, `employees`, `subscription`, `invoice`, `benefitGrants`, `benefitUsages`. Денежные поля обозначены `Kopecks`. Итоги отчёта относятся ко всему оплаченному периоду компании; фильтры меняют только детализацию и не распределяют полную абонентскую плату между сотрудниками.

Ошибки: `{"code":"personal_limit","message":"Недостаточно личного лимита.","details":null}`. Основные статусы: `401` — нет/истекла сессия; `403` — нет прав/доступ отключён; `404` — объект своей компании не найден; `409` — конфликт, лимит или неактивная подписка; `422` — неправильные поля/даты; `503` — БД недоступна. SQL и пароли в ответ не включаются.

## Проверки

`backend/tests` работает на настоящем PostgreSQL в отдельных схемах `test_<uuid>`. Приложенческие таблицы не очищаются. Покрыты параллельные списания, повтор запроса, общий и личный лимиты, RBAC, изоляция компаний, истечение/отзыв сессии, тарифные места, календарные фильтры, отказ подписки на паузе/с истёкшим сроком, сброс и модель экономики.

`npm --prefix frontend run test:api` вызывает реальный frontend-адаптер через HTTP. Использует отдельного `demo_other_admin`; если у него уже есть компания, проверка прекращается без её изменения. Удаляется только созданная самим прогоном тестовая компания. Сверяются также все 6 экономических сценариев frontend/API.

## Границы

Пока один действующий тариф/счёт на компанию, без автопродления. Настоящий платёжный шлюз, B2C, P1-брони/курьеры, уведомления и публичная аутентификация не подключены. Тарифы версии 1 не перезаписываются при seed. Старое localStorage-демо не импортируется автоматически и не удаляется при серверном сбросе.

Реализация опирается на [FastAPI Security](https://fastapi.tiangolo.com/tutorial/security/simple-oauth2/) и [SQLAlchemy ORM](https://docs.sqlalchemy.org/en/20/orm/queryguide/select.html).
